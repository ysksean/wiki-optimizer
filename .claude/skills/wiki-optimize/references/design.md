# Design a wiki for a real task

## Start with the decisions the reader must make

Write a compact brief using known context. Include the reader (human, agent, or
both), the work they need to accomplish, the moment they consult the wiki, source
locations, output destination and relevant constraints. Mark assumptions as such.

Capture a representative set of questions in the user's own terms. Include the
questions whose failure would make the wiki unusable; mark those as must-answer.
Use factual lookup, how/why, cross-source comparison and missing-evidence cases
when relevant to the task. Do not add categories or a fixed question count merely
to fill a template. Keep user acceptance questions separate from any questions
generated by Stage 0. Putting examples in its task prompt does not make those
examples its fixed evaluation set.

Example of a task-oriented question: “A deployment health check failed; which
version should I restore and who authorizes it?” Its route may cross a runbook
and an approval policy. Do not force it into a single summary page.

## Inspect evidence before choosing folders

Read a small representative slice of each relevant source type, then inspect
the passages needed for must-answer questions. Record the source's role: current
policy, implementation, historical decision, worked example or unverified note.
If sources disagree, preserve dates and scope and mark the conflict for resolution.
A directory tree, code symbol or document heading is a discovery clue, not proof
of an answer. No evidence found in a capped scan means “not established in this
scan,” not necessarily “the knowledge does not exist.”

For an existing wiki, inspect its entry index, page conventions, links and source
references. Identify which paths must remain stable. Prefer a targeted change
when the current structure already serves the main tasks.

## Define each page's job

Choose grouping boundaries based on reader questions and how the material changes.
Use a second candidate organization only when there is a consequential tradeoff
(for example, lifecycle versus component ownership). Explain that tradeoff briefly.
There is no universal ideal number of pages or directory depth.

For each proposed page specify:

| Field | What to decide |
|---|---|
| `path`, `title` | Stable, distinguishable location and name |
| `purpose` | The question or decision this page serves; avoid generic “overview” |
| `outline` | Sections sufficient to answer that question |
| `sources` | Actual original paths and, where useful, verified section anchors |
| `status` | `grounded` when sources are linked, `gap` otherwise |

Add design notes where needed: what belongs elsewhere, related pages, conflict
handling, and what source change should trigger an update. Do not invent owners,
review cadences or policies the user has not established.

Keep canonical facts in one place and link from other pages. Preserve exceptions,
preconditions, numeric thresholds, units, rationale and version constraints that
matter to the task. A generic folder list without page responsibilities is incomplete.

If using Stage 0, its current prompt requests 5–12 pages. Treat this as an engine
default, not evidence that the task needs that many. A manually edited candidate
must have its own reviewed artifact; the original run's score no longer measures it.

## Check source references and real navigation

The optional local checker is deterministic and makes no LLM calls:

```bash
python3 .claude/skills/wiki-optimize/scripts/check_design.py \
  --design /absolute/path/design.json --source /absolute/path/source-root
```

It accepts `{"pages": [...]}` or an existing Stage 0 `report.json`. Use repeated
`--source` flags for multiple roots; otherwise a report's `sources` are used.
The source namespace is `<root-basename>/<relative-path>`, matching `repo_map.py`.
The checker reports path/reference/anchor problems, repeated purposes and gap pages.
It does not prove semantic grounding or question-answer quality. Root basenames
must be distinct; ambiguous source namespaces require narrowing or reorganizing inputs.

Next, walk the representative questions from the entry index:

1. Using only the index and link descriptions, identify the pages a reader would choose.
2. Read those pages (or their source passages if the output is still a skeleton).
3. Record whether the answer is supported, navigation is ambiguous, content is
   missing, sources conflict, or evidence has not been obtained.
4. Fix the page's responsibility, source mapping, index description or missing
   content according to the failure. Do not solve every failure by reading everything.

Keep a compact route table: question, must-answer, entry → pages, supporting
source, result and unresolved issue. Report separately whether this was a human/
assistant inspection or an actual consumer-agent run. Source-based checks of a
skeleton cannot be reported as successful retrieval from finished wiki pages.

Use the actual consumer's reading behavior when evaluating a finished wiki. The
built-in B router uses a flat index and whole-page reads; it does not measure
filesystem search, recursive link traversal or section-level reading.

## Deliver and retain the design

For a substantive design task, save `DESIGN.md` and machine-readable `design.json`
in the chosen task output directory. `DESIGN.md` contains the brief, page tree and
responsibilities, route table, source gaps/conflicts, reasons for key boundaries,
and update rules. `design.json` uses the page fields above and a top-level `sources`
list of absolute source root directories so later sessions can resolve references.
Keep the reviewed run path with the design.

For a lightweight sketch, a concise response can be sufficient. For “build it,”
continue into content creation: populate grounded pages from the verified sources,
retain provenance, link the index and related pages, and check the actual output.
Leave gap pages clearly marked with what evidence is needed. Do not present empty
stubs as a working wiki.

For a redesign, include the mapping from old paths to proposed paths and a diff;
preserve or update links when moving pages. For future additions, state the trigger
and affected pages. Use the incremental tool only when its input assumptions hold.
