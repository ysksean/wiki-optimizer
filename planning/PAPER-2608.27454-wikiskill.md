## 1. 세 줄 요약

에이전트 스킬을 반복 개선할 때, 그동안 배운 것이 최적화 이력 여기저기 흩어져 재사용되지 않는다는 문제를 제기한다. WikiSkill은 원본 실행 기록(raw)과 실행 가능한 스킬(skills) **사이에 구조화된 지식층(wiki)을 끼워 넣고**, 스킬은 검증 점수로 롤백하되 **위키는 절대 롤백하지 않고 계속 쌓는다**. 벤치마크 5종 × 모델 5종에서 기존 스킬 진화 기법(Trace2Skill/EvoSkill/SkillOpt)을 앞섰고, ablation으로 "위키가 없으면 이득도 없다"를 보였다.

논문이 명시적으로 출발점 삼은 것은 Karpathy의 **LLM Wiki** 관점이다 (`karpathy2026llmwiki` 인용). 형님 개인 위키(`llm_wiki`)와 이 프로젝트가 같은 뿌리에서 나온 셈이다.

## 3. 논문이 실제로 새로 주는 것

### 3-1. "이력"과 "위키"는 다르다 — 그리고 그 차이가 논문의 최대 주장

우리 `_history_block`이 reflect에 넣는 것은 전략 문자열 200자 잘라낸 목록이다. 논문의 위키는 다르다:

- `wiki/patterns/*.md` — 패턴 1개당 페이지 1개. **무엇이 문제인가 + 왜 그런가(근본 원인) + 어떤 명령이 실제로 실패/성공했나 + 구체적 해법**. 10~30줄 권장
- `wiki/index.md` — 한 줄 요약 카탈로그. 형식이 강제된다: `문제 + 근본 원인 + 해법`을 한두 문장에
- `wiki/logs.md` — 반복 회차별 발견 누적
- 수정은 patch 방식 (`append`/`replace`/`insert_after`) — 통째 재작성 금지

논문의 ablation(Table 3, Gemini-3.5-Flash):

| Inference 위키 접근 | Proposer 위키 접근 | 평균 |
|---|---|---|
| 스킬 없음 | | 40.4 |
| ✅ | ❌ | 45.3 |
| ❌ | ❌ | 48.7 |
| ✅ | ✅ | 60.9 |
| ❌ | ✅ (기본 설정) | **63.7** |

**48.7 → 63.7 (+15.0%p)** 가 "구조화된 위키가 있고 없고"의 차이다. 그리고 여기서 중요한 지점: 위키 없는 조건(48.7)도 EvoSkill 식의 flat 이력은 갖고 있다. 즉 논문이 주장하는 것은 "이력 vs 무이력"이 아니라 **"flat 이력 vs 구조화 위키"** 다.

> 우리 `evolve-nohist` ablation은 "이력 있음 vs 없음"을 재고 있다. 논문의 진짜 대비축과 다르다. 우리 실험대에 arm을 하나 더 붙이면 논문의 최대 주장을 직접 재현하거나 반증할 수 있다.

### 3-2. 통계적 유의성 검정

논문은 paired bootstrap 1,000회로 검정하고, `p < 0.05`로 모든 경쟁자를 이기지 못하면 **단독 1위를 선언하지 않는다**. 통계적으로 구분 안 되는 것들은 공동 1위로 묶어 굵게 표시한다.

우리 `aggregate()`는 순효과(evolve 향상폭 − control 향상폭)를 **점 추정 하나로만** 낸다. `wiki-optimize` 스킬이 사용자에게 "이 개선이 진짜인가"를 판정해준다고 말하고 있는데, 그 판정의 근거가 점 추정 하나다. 이건 우리 프로젝트의 산출물 자체가 걸린 문제다.

### 3-3. 층화 샘플링 예산

Wiki Maintainer에 넣는 실행 기록: 반복당 최대 8건, **실패 5 + 성공 3**으로 층화, 각 기록 15,000자 캡. 성공 사례를 일부러 섞는 이유는 잘 되던 동작의 퇴행을 막기 위해서다.

우리 reflect는 틀린 질문만 본다. 맞은 질문이 왜 맞았는지는 안 본다.

### 3-4. Proposer를 ReAct로 — 비용이 학습셋 크기와 무관해진다

미리 잘라 넣은 기록을 받는 대신, Proposer가 index를 먼저 보고 `read_file`로 필요한 패턴/기록만 골라 읽는다. 결과적으로 최적화 LLM 호출이 반복당 `1 + T_ReAct` (T는 10~20)로 **학습셋 크기와 무관한 O(1)**. Trace2Skill은 기록 하나당 호출 하나라 O(N).

## 4. 논문이 우리보다 약한 곳 — 따라가면 안 되는 부분

**논문에는 대조군(control arm)이 없다.**

논문의 gating은 `R(val) > R_best`, 즉 검증 점수 최고 기록 갱신이다. 이건 우리가 [batch.py](src/batch.py) 문서 주석에서 스스로 지적한 **"best-of-N 노이즈로 생기는 가짜 향상폭"** 에 그대로 노출된다. K번 반복하며 최고값만 취하면, 진화가 전혀 없어도 점수는 올라간다.

논문은 "스킬 없음" 기준선과는 비교하지만, **"진화 없이 K회 재샘플링"** 대조군은 돌리지 않는다. 우리 `control` arm이 바로 그것이고, 이 축에서는 **우리 방법론이 논문보다 엄격하다.**

저자들도 Limitations에서 strict gating이 "당장은 점수를 유지하지만 다음 회차에 이득이 될 중립적 제안"을 배제한다고 인정한다. 다만 노이즈 편향은 언급하지 않는다.

부수적으로 논문이 인정한 다른 한계들:

- **위키 가지치기 장치가 없다** — 패턴·로그·diff가 무한 누적. 긴 실행에서 문제가 될 거라고 스스로 적었다. 우리 jsonl도 같은 구조인데, 읽을 때 `n_rejected=5 / n_accepted=3`으로 자르는 덕에 프롬프트 폭주만 면하고 있다 (파일 자체는 계속 커진다).
- **스킬 검색/triggering을 평가 안 했다** — 스킬을 프롬프트에 통째로 주입해 검색 실패를 실험 변수에서 제거했다. 실전 하네스는 progressive disclosure라 조건이 다르다.

## 5. 우리 조건에서의 결정적 차이 — 평가 함수

논문의 벤치마크 5종(LiveMath, SealQA, SpreadSheet, OfficeQA, ALFWorld)은 **정답 라벨이 있다.** 채점이 결정론적이다.

우리는 LLM judge가 요약 기반 답변의 정답 여부를 판정한다. 노이즈 축이 하나 더 있고, 우리는 이미 그 대가를 치렀다 — SEA-13에서 judge 파싱 실패가 0점으로 조용히 메워져 실험 결론을 오염시키던 경로를 막았다.

**논문의 수치(+15.0%p 같은)를 우리 환경에서 그대로 기대하면 안 된다.** 논문의 효과 크기는 결정론적 채점 위에서 측정된 것이다. 우리 실험대에서는 같은 기법이 judge 노이즈에 묻힐 수 있고, 그걸 구분하는 게 정확히 control arm과 유의성 검정의 역할이다.

## 6. 적용 권고

### P1 — paired bootstrap 유의성 검정 (권장, 즉시)

`batch.aggregate()`에 순효과의 신뢰구간과 p값을 붙인다. 논문 방식 그대로: 테스트 인스턴스를 복원추출로 1,000회 리샘플링, arm 간 차이의 분포를 만든다.

- **비용**: LLM 호출 0. 순수 계산. 기존 run 결과 CSV에 소급 적용도 된다
- **효과**: "순효과 +3.2점"이 "+3.2점 (95% CI −1.1 ~ +7.4, p=0.21)"이 된다. 지금 우리가 못 하는 판정을 하게 된다
- **위험**: 낮음. 기존 산식을 안 건드리고 옆에 붙인다
- **주의**: run 수가 적으면 대부분 유의하지 않게 나올 것이다. 그게 사실이고, 그 사실을 아는 게 이 작업의 목적이다

### P2 — 구조화 위키 arm 추가 (권장, 실험적 가치 큼)

`evolve`/`evolve-nohist`/`control` 옆에 `evolve-wiki` arm을 붙인다. flat jsonl 대신 pattern 페이지 + index를 유지하고, reflect가 그걸 읽는다.

- **비용**: 반복당 Wiki Maintainer LLM 호출 1회 추가. arm 하나 늘어나니 배치 시간도 늘어난다
- **효과**: 논문의 최대 주장을 우리 실험대에서 검증한다. 우리 프로젝트가 하려는 일이 정확히 이런 판정이다
- **왜 지금 할 만한가**: 3-arm 인프라(`batch.py`의 arm 루프, 문서당 질문 세트 공유)가 이미 있다. 배선이 아니라 arm 정의만 추가하는 일이다
- **선행 조건**: P1. 유의성 검정 없이 이 arm을 돌리면 결과를 해석할 수 없다

### P3 — B단계(구조 진화)에 이력 주입

[evolve_structure.py:73](src/evolve_structure.py:73)은 이력을 전혀 안 쓴다. SEA-15가 지금 대조군을 붙이는 중인데, 그게 머지되면 A/B 단계의 증거 기준이 맞춰진다. 이력은 그 다음이다.

- **비용**: 낮음. A단계 `_history_block`을 재사용
- **선행 조건**: SEA-15 머지

### P4 — Skills Layer 진화 (보류 권고)

논문의 진짜 대상은 스킬 문서(`SKILL.md`)다. 우리 하네스 프롬프트(`harness/prompts/pipeline.md`)나 `~/.claude/skills/`를 진화 대상으로 삼는 확장이 자연스러워 보인다.

**하지만 지금은 하지 말자.** 평가 함수가 없다. 논문의 루프는 `R(val)`이라는 검증 점수로 굴러가는데, 우리 하네스에는 정답 라벨이 붙은 작업 데이터셋이 없다. 점수 없이 이 루프를 돌리면 "LLM이 프롬프트를 계속 고쳐 쓰는데 나아졌는지 알 수 없는" 상태가 된다. 그건 진화가 아니라 표류다.

먼저 필요한 것: 하네스 작업의 성공/실패를 판정할 수 있는 소규모 데이터셋. 그게 생기기 전엔 P4는 열리지 않는다.

## 7. 검토 결론

논문의 아이디어 대부분은 우리가 이미 갖고 있다. 진짜로 새로운 것은 **(a) 이력을 flat 목록이 아니라 구조화된 패턴 지식으로 유지하는 것**과 **(b) 개선이 진짜인지 통계로 판정하는 것** 둘이다.

그리고 이 논문은 우리 대조군 설계를 강화해주기보다는, **우리 설계가 이 축에서는 더 엄격하다는 것을 확인시켜준다.** 논문을 따라가면서 control arm을 버리는 것은 퇴보다.

제안 순서: **P1 → P2 → P3**, P4는 평가 데이터셋이 생길 때까지 보류.
